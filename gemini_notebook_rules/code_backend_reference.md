# バックエンド・データパイプライン仕様書 (code_backend_reference.md)

※データベースの物理スキーマ（Supabaseの各テーブル構造）は別ファイルのリファレンスを参照すること。
本ドキュメントでは、バックエンドで実行されるセイバーメトリクス等の「独自指標計算ロジック」および「データ取得の前提条件」を定義する。フロントエンドで再計算やUI表示の出し分けを行う際は、必ず以下のロジックに完全準拠すること。

## 1. データ取得とパイプラインの前提知識
- **スクレイピング技術:** データ抽出（スクレイピング）はPythonではなく **JavaScript (Node.js/Playwright)** を使用して取得している。AIはPythonのBeautifulSoup等を使用したスクレイピングコードを提案しないこと。
- **処理フロー:** Node.jsで取得した生データを、Pythonスクリプト（`get_npb_...` 等）で整形し、さらに `calc_...` スクリプト群で以下のセイバー指標を付与した上で、Supabaseへアップロード・更新（補完）を行っている。

## 2. 独自指標の計算ロジック（コアアルゴリズム）

### 2.1 打撃指標（Batting Metrics）
- **wOBA (Weighted On-Base Average)**
  - 分子: `0.69*(四球-故意四) + 0.72*死球 + 0.89*単打 + 1.27*二塁打 + 1.62*三塁打 + 2.10*本塁打`
  - 分母: `打数 + (四球-故意四) + 犠飛 + 死球`
- **wRC+**
  - `(((wOBA - リーグ平均wOBA) / 1.2) + 0.120) / 0.120 * 100`
- **wRAA**
  - `((wOBA - リーグ平均wOBA) / 1.2) * 打席`
- **BABIP**
  - `(安打 - 本塁打) / (打数 - 三振 - 本塁打 + 犠飛)`
- **IsoD**
  - `出塁率 - 打率`
- **K% / BB%**
  - K%: `(三振 / 打席) * 100`
  - BB%: `(四球 / 打席) * 100`
- **野手WAR（超重要）**
  - `WAR = (wRAA + (ポジション補正値 * (打席 / 600)) + (20 * (打席 / 600))) / 10`
  - **ポジション補正値 (600打席換算)** ※ `position_detail` の文字列で完全一致判定
    - 捕: `+12.5` | 遊: `+7.5` | 二 / 中: `+2.5` | 外: `-7.5` | 一: `-12.5` | 指: `-15.0`
- **roman（ロマン度）** ※現役選手(is_active_season)のみ
  - `ISOp + (三振 / 打席) - 打率` （※ただし ISOp >= 0.150 の場合のみ計算。満たない場合は 0.0）
- **cospa（コスパ）** ※2026年の現役選手のみ
  - `野手WAR / 年俸(億円)`

### 2.2 投手指標（Pitching Metrics）
- **投球回（IP）の十進法変換（超重要）**
  - データベース上の文字列（例: "1.1", "1.2"）は、計算前に必ず以下で数値変換する。
  - `.1` は `1/3` (0.333...)、`.2` は `2/3` (0.666...) として扱う。
- **FIP (Fielding Independent Pitching)**
  - `FIP = ((13 * 本塁打) + 3 * (四球 + 死球) - (2 * 三振)) / 投球回 + リーグFIP定数`
  - ※リーグFIP定数 = `リーグ防御率 - ((13*Lg_HR + 3*(Lg_BB + Lg_HBP) - 2*Lg_SO) / Lg_IP)`
- **RSAA (Runs Saved Above Average)**
  - `RSAA = (リーグ平均ERA - FIP) * (投球回 / 9)`
- **投手WAR**
  - `WAR = (RSAA / 10) + (投球回 * 0.03)`
- **WHIP**
  - `(四球 + 安打) / 投球回`
- **K-BB%**
  - `((三振 - 四球) / 打者) * 100`
- **BABIP**
  - `(安打 - 本塁打) / (打者 - 三振 - 四球 - 死球 - 本塁打)`
- **LOB%**
  - `((安打 + 四球 + 死球 - 失点) / (安打 + 四球 + 死球 - 1.4 * 本塁打)) * 100`
- **unluck（不運度）** ※現役選手のみ
  - `防御率 - FIP`
- **先発判定** ※現役選手のみ
  - `(投球回 / 登板数) >= 3.0` の場合 `1`（先発判定）、それ以外は `0`。
- **cospa（コスパ）** ※2026年の現役選手のみ
  - `投手WAR / 年俸(億円)`

  ## 3. インフラ・運用アーキテクチャ（データ更新パイプライン）
本プロジェクトはフロントエンド（映写機）とバックエンド（工場）を完全に分離したハイブリッド構造を採用している。AIはこの境界線を越えるような設計（例：Next.js側でのスクレイピングや重いバッチ処理の提案）を絶対に行わないこと。

### 3.1 システム分離の原則
- **フロントエンド (Vercel / Next.js):** データの更新や複雑な集計処理は持たず、Supabaseから取得した完成済みデータを高速描画することに専念する。
- **バックエンド (GitHub Actions / Python):** データの収集、名寄せ、セイバーメトリクスの計算、DBへのUPSERTはすべてPythonスクリプトが担い、GitHub Actions（`daily_scrape.yml`）によって自動で定期実行される。

### 3.2 コアバッチスクリプトの役割
- **`sync_team_stats.py`:** 1軍の全データ更新を担う司令塔。スポナビからの生データ取得、wOBAやWARの計算、`batting_stats` 等への保存をすべて行う。
- **`sync_profiles.py`:** オイシックス等の2軍（ファーム）選手プロフィールを抽出し、`farm_players` を拡充するスクリプト。
- **`fetch_daily_performance.py`:** その日の試合ログを日次で取得し、`daily_performance` へ流し込む。

### 3.3 データ連携・名寄せの絶対法則
- PythonからSupabaseへデータをインサート・更新する際、選手を特定する「名寄せ」のロジックは **「文字列の完全一致（すべての空白・スペースの除去、およびNFKC正規化後）」** を絶対基準としている。
- したがって、DB側（マスタ）のデータ精度が命であり、フロント・バックエンド問わず「登録名の揺らぎ」を安易にハードコードで吸収しようとせず、正規化処理を通すこと。
