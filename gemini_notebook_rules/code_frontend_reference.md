# 【全文】 フロントエンド・UI設計仕様書 (code_frontend_reference.md)

本ドキュメントは、Next.js（フロントエンド）におけるデータフォーマットの共通ルール、および各画面におけるUIコンポーネントの構造規則を定義する。AIはコード生成や修正を行う際、既存のUIレイアウトやデザイン秩序を破壊しないよう、以下のルールを絶対厳守すること。

---

## 1. 共通ユーティリティ・フォーマット関数
フロントエンドでの数値表示・計算は、野球データとしての慣習と正確性を守るため、必ず以下のロジック（または同等の既存関数）を介さなければならない。

- **`dotFormat(val)` (必須項目)**
  - 打率、wOBA、ISOp、OPSなど「0.xxx」となる値は、先頭の0を省略して「.xxx」と表記すること。
  - マイナス値の場合は「-.xxx」とする。値が0の場合は「.000」とする。
  - コード内に実装されている `dotFormat` 等のフォーマット関数を「UIの整理」や「コードの簡略化」を理由に削除・変更することを厳禁とする。
- **`formatIP(ipStr)`**
  - 投球回の `.1` は `1/3`（0.333...）、`.2` は `2/3`（0.666...）として厳密に十進法に変換してから各種指標の計算に用いること。
- **通算投球回の計算処理**
  - 複数年や複数選手の投球回を合算する際は、小数の単純計算による誤差を防ぐため、必ず一度「総アウト数（`ip * 3`）」に変換して足し合わせ、最後に `整数.端数`（例: 143.1）の形式に逆変換して文字列として出力すること。

## 2. ランク判定とバッジデザイン
`getRank` 関数等のランク判定ロジック、および画面上のバッジ配色（Tailwind CSS）は、2026年版エビデンスに基づく以下の基準数値を絶対に使用して評価を行い、いかなる場合も現状を100%維持すること。

### 2.1 ランク判定基準値
- **総合指標 (野手・投手共通)**
  - **WAR:** SSS: >6.0, SS: >4.5, S: >3.0, A: >1.5, B: <=1.5
- **投手指標**
  - **FIP:** SSS: <2.10, SS: <2.60, S: <3.10, A: <3.70, B: >=3.70
  - **K/9:** SSS: >11.5, SS: >10.5, S: >9.5, A: >8.5, B: <=8.5
  - **K-BB%:** SSS: >25.0%, SS: >20.0%, S: >15.0%, A: >10.0%, B: <=10.0%
- **打者指標**
  - **wRC+:** SSS: >175, SS: >155, S: >135, A: >115, B: <=115
  - **wOBA:** SSS: >.400, SS: >.370, S: >.340, A: >.310, B: <=.310
  - **OPS:** SSS: >1.000, SS: >.900, S: >.820, A: >.750, B: <=.750
  - **ISOp:** SSS: >.250, SS: >.200, S: >.160, A: >.120, B: <=.120

### 2.2 バッジ配色ルール (`rankBadge`)
「パワプロ」のようなポップで高コントラストなライトモードのデザイン基準を徹底し、ダークモードや視認性を低下させる低コントラストな配色・文字は避けること。
- **SSS:** `bg-gradient-to-b from-yellow-300 via-orange-500 to-red-600 animate-bounce text-white font-black italic rounded-lg`
- **SS:** `bg-slate-400 text-white font-black italic rounded-lg`
- **S:** `bg-amber-500 text-white font-black italic rounded-lg`
- **A:** `bg-blue-500 text-white font-black italic rounded-lg`
- **B:** `bg-gray-500 text-white font-black italic rounded-lg`

## 3. 選手個別ページ（`app/player/[id]/page.tsx`）の設計ルール
選手個別の成績表示において、AIによる独断での項目省略やレイアウト変更は重大なバグとみなし、以下のルールを絶対条件とする。

- **項目数と日本語ラベルの厳守**
  - 画面上の日本語ラベル（高校、大学、基本成績など）を勝手に英語化しないこと。
  - 以下の「投手22項目・打者21項目」および「分析指標」を絶対に省略・非表示にせず、すべて維持すること。
    - **投手基本（22項目）:** 防御率、登板、勝利、敗戦、セーブ、ホールド、HP、完投、完封、無四球、勝率、打者、投球回、安打、本塁打、四球、死球、三振、暴投、ボーク、失点、自責点
    - **投手分析:** 投手WAR、FIP、WHIP、K/BB、K-BB%、K/9、BB/9
    - **打撃基本（21項目）:** 打率、試合、打席、打数、得点、安打、二塁打、三塁打、本塁打、塁打、打点、盗塁、盗塁刺、犠打、犠飛、四球、死球、三振、併殺打、出塁率、長打率
    - **打撃分析:** 野手WAR、wOBA、wRC+、OPS、ISOp
- **アコーディオン型グリッドレイアウトの維持 (重要)**
  - スマホでの視認性を最優先（画面右側に要素が切れないモバイルファースト設計）とするため、選手個別ページではHTMLの `<table>` タグを使用せず、**開閉式アコーディオンカード構造**を維持すること。
  - 詳細項目を展開するエリアは、必ず `grid grid-cols-4 md:grid-cols-6 lg:grid-cols-8 gap-y-6 gap-x-2 text-center text-xs` による可変グリッド設計とすること。
- **既存CSSクラスの完全保護**
  - レイアウト崩れや透過バグを防ぐために配置されている既存のCSSクラス（特に `sticky`, `z-index`, `shadow`, `bg-white` など）は、指示がない限り1文字も削除・変更してはならない。

## 4. ツールチップ（`HelpIcon`）の配置ルール
セイバーメトリクス指標（wOBA, wRC+, WAR, FIPなど）を表示する際は、初見ユーザーのアクセシビリティを担保するため、必ず `HelpIcon` コンポーネントを併記すること。
- 「指標の解説（`text`）」と「評価の目安（`benchmark`）」を確実に内包したツールチップをポップアップ表示させる構造を維持すること。

---

## 5. 動的計算（フロントエンド側処理）
フロントエンド側でのWARやwRC+、OPS等の動的再計算、あるいは通算成績（Career Total）の算出時には、以下の仕様に従うこと。
- **補正値の適用:** `PARK_FACTORS`（球場補正値・PF）および `POSITION_ADJUSTMENT`（ポジション補正値）の定数オブジェクトを参照し、厳密にロジックへ加味すること。
- **ポジション補正の判定:** WAR算出時のポジション補正は、データベースの `position_detail` カラムの文字列との「完全一致」で判定すること。

## 6. ランキング画面（`app/ranking/page.tsx`）の設計ルール
複数の選手を比較・ソートして表示する総合リーダーボード画面では、以下のルールを厳守すること。

- **`<table>` タグの使用禁止:** 比較画面であっても表組み（横長のTable）は使用せず、`flex` と `grid` を駆使した「カード型リスト（`<Link>` ブロックの繰り返し）」で構成すること。要素が画面右側に切れるのを防ぐため、適切な横スクロールやモバイルファースト設計を徹底すること。
- **状態管理（URLパラメータ駆動）:** 1軍/2軍（`level`）、野手/投手（`role`）、ソートキー（`sort`）などの絞り込み・並び替え状態は、必ずURLパラメータ（`useSearchParams`）で一元管理し、URLの共有によって全く同じランキングが再現できる設計を維持すること。
- **指標ごとの条件分岐表示:** `roman` や `cospa`, `unluck` などの特殊指標でソートされた場合は、`renderSubMetrics` 関数を用いて、選手名の下部にその指標を構成する重要な要素（例：ロマン度の場合は ISOp / K% / 打率）をバッジ形式でハイライト表示すること。

## 7. トップページ（`app/page.tsx`）の設計ルール
出身校や地元など、あらゆる文脈から集計を行うルーツ別ランキング画面では、以下の仕様に従うこと。

- **投球回（IP）の特殊加算ロジック (`addIP`):** 複数選手の投球回、または日次パフォーマンスを合算する際は、単純な小数加算を行ってはならない。必ず小数を「アウト数（1/3）」として扱い、3アウトで1イニングに繰り上げる専用の計算関数 `addIP` を通すこと。
- **ネイティブアコーディオンUI:** ランキングの各行には `<details>` と `<summary>` タグを使用した開閉式リスト構造を採用し、展開時に「主な活躍選手（`players.map`）」をカード形式で表示する設計を維持すること。
- **ハイブリッドな状態管理:** 期間（`period`）やカテゴリ（`cat`）といったURL共有が必要な条件は `useSearchParams` で管理し、1軍/2軍や野手/投手の即時タブ切り替えは `useState` で管理する設計方針を継承すること。

---

## 8. ルーツ別詳細ページ（`roots/[type]/[name]/page.tsx`）の設計ルール
特定のルーツに属する現役選手一覧を深掘りする詳細ページでは、以下の特有ルールを厳守すること。

- **割合指標における規定未満の分離表示 (`useSplit`):**
  打率（`avg`）、防御率（`era`）、OPS、wRC+ などの割合・平均指標（レートスタッツ）でソートした場合、一覧を「規定到達者（`qual`）」と「規定未満者（`unqual`）」に分割する。規定未満者は `参考記録（規定未満）` のディバイダーの下に配置し、要素を半透明（`opacity-80 bg-slate-50/50`）にして視覚的に区別すること。
- **積み上げ指標におけるシーズン推計ペースの表示 (`showPace`):**
  本塁打、安打、勝利数、奪三振などの積み上げ指標（カウンティングスタッツ）でソートしており、かつシーズン途中（`team_games < 143`）である場合は、現在の消化試合数から算出したシーズン終了時の着地推計値 `(statValue / team_games) * 143` を計算し、「（〇〇 ペース）」としてUI上に必ず併記すること（※WARやロマン度、コスパ等の計算値も含む）。
- **カード型デザインの維持:**
  このページにおいても `<table>` タグの使用は厳禁とし、`<Link>` タグをラッパーとしたカード型UI（`flex`, `grid`）を維持すること。
